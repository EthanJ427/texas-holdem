# 联机协议

朋友局用的多人协议。一张桌子一个房间，服务器是唯一权威。

## 总体形态

- **传输**：WebSocket，JSON 文本帧
- **权威**：服务器持有牌堆和所有人的底牌，客户端只是渲染层
- **状态下发**：只发 `engine.viewFor(玩家id)` 的产物，绝不序列化引擎本身

### 一个刻意的决定：每次都发全量状态，不做增量

一张六人桌的裁剪视图大约 1～2 KB，一手牌撑死几十次变更。相比之下，增量同步会带来一整类「客户端和服务器慢慢对不上」的 bug，而这类 bug 极难复现也极难排查。

**用带宽换正确性，这里换得很值。**

事件流（`events`）只用来播动画，不参与状态推导 —— 就算某条事件丢了或者播晚了，下一份 `state` 也会把画面拉回正确。

---

## 消息信封

所有消息统一外层结构：

```json
{ "t": "action", "id": 17, "d": { } }
```

| 字段 | 含义 |
|---|---|
| `t` | 消息类型 |
| `id` | 客户端自增的消息编号，仅客户端发出的消息需要 |
| `d` | 负载 |
| `re` | 服务器回应时带上，指明在回应哪条 `id` |

## 客户端 → 服务器

### `join` — 进入房间

```json
{ "t": "join", "id": 1, "d": {
    "room": "K7QP",
    "name": "老王",
    "token": "上次拿到的 sessionToken，首次进入时省略"
}}
```

`token` 是重连的凭据。带上有效 token 就能拿回原来的座位和筹码。

### `sit` / `stand` — 坐下 / 离座

```json
{ "t": "sit",   "id": 2, "d": { "seat": 3 } }
{ "t": "stand", "id": 9, "d": {} }
```

`seat` 省略则由服务器分配。牌局进行中离座不会立刻生效，会等这一手打完。

### `action` — 行动

```json
{ "t": "action", "id": 12, "d": {
    "handNumber": 47,
    "actionSeq": 6,
    "type": "raise",
    "amount": 120
}}
```

`amount` 是**加注到的总额**，不是增量 —— 和单机引擎的语义一致。

## 服务器 → 客户端

### `welcome` — 握手结果

```json
{ "t": "welcome", "re": 1, "d": {
    "you": 3,
    "token": "...",
    "room": "K7QP",
    "serverTime": 1786300000000,
    "config": { "smallBlind": 10, "bigBlind": 20, "startingChips": 1000,
                "turnSeconds": 60, "fillWithBots": true }
}}
```

`serverTime` 用来对时（见「倒计时」一节）。

### `state` — 全量裁剪状态

```json
{ "t": "state", "d": {
    "view": { "…engine.viewFor(you) 的产物…" },
    "actionSeq": 6,
    "seats": [ { "seat": 0, "name": "老王", "connected": true, "isBot": false } ]
}}
```

`view` 的字段就是引擎里那份，已经受 `VIEW_KEYS` 白名单测试保护。

### `events` — 动画流

```json
{ "t": "events", "d": { "events": [
    { "type": "action", "player": 2, "action": "call", "amount": 20, "text": "…" },
    { "type": "street", "street": "flop", "board": [12, 30, 7], "text": "…" }
]}}
```

来自引擎的 `drainEvents()`，但**必须先过 `eventsFor()` 再发**。

事件是状态之外的第二条出口，很容易被忽略：`showdown` 和 `hand-end` 事件里直接挂着 `hands` / `result`，其中的 `best`（取胜的五张）含底牌。现在它恰好只包含没弃牌的人，但那是引擎内部实现的巧合，不是被守住的约束。

所以定死一条规则：**事件只负责播动画，一律不携带牌面数据**。公共牌是公开的可以留；摊牌要亮的牌，客户端从 `state` 里拿——那份已经裁剪过。`eventsFor()` 会摘掉 `hands` 和 `result`，同样受白名单（`EVENT_KEYS`）测试保护。

### `turn` — 轮到谁了

```json
{ "t": "turn", "d": {
    "seat": 3,
    "actionSeq": 6,
    "deadline": 1786300025000,
    "legalActions": [ { "type": "fold" }, { "type": "call", "amount": 20 },
                      { "type": "raise", "min": 40, "max": 980 } ]
}}
```

只有轮到自己时 `legalActions` 才非空 —— 这一点在引擎的 `viewFor` 里已经保证了。

### `error`

```json
{ "t": "error", "re": 12, "d": { "code": "stale_action", "message": "这一手已经推进了" } }
```

| code | 什么情况 |
|---|---|
| `room_not_found` | 房间号不存在 |
| `room_full` | 六个座位都满了 |
| `bad_token` | 重连凭据无效或过期 |
| `not_your_turn` | 没轮到你 |
| `stale_action` | 手牌号或动作序号对不上（详见下节） |
| `illegal_action` | 动作本身不合法（金额越界等） |

## 防重放：手牌号 + 动作序号

**要解决的问题**：双击、网络重发、断线重连后客户端把旧动作又发一遍 —— 任何一种都可能让同一个动作被执行两次，直接导致筹码错乱。

**做法**：服务器为每一手维护一个 `actionSeq`，每接受一个动作就 +1。客户端发动作时必须带上它**以为**的 `handNumber` 和 `actionSeq`。

服务器三项全中才执行：

1. `handNumber` 等于当前手牌号
2. `actionSeq` 等于服务器当前值
3. 发送者确实是当前行动人

任一不符 → 回 `stale_action`，**不改变任何状态**。

于是重复提交天然安全：第二条的 `actionSeq` 必然已经过期。这比"给每个动作一个唯一 id 然后去重"更简单，因为扑克本来就是严格串行的 —— 序号自然存在，不用另造一个。

> Cloudflare Durable Objects 在这里有额外便利：一张桌子一个对象、天然单线程，两个请求不可能真正并发进入。序号仍然要做，因为它防的是**客户端**重发，不是服务器并发。

## 倒计时

**必须由服务器计时**，放客户端就能改。

- 每个决定给 **60 秒**（朋友局节奏，不用赶）
- 服务器在 `turn` 里给出 `deadline`（绝对时间戳，服务器时钟）
- 客户端用 `welcome` 里的 `serverTime` 算出本地时钟偏移，据此画倒计时
- 到点服务器替他行动：**能过牌就过牌，否则弃牌**
- 服务器实际等到 `deadline + 1.5s` 才动手，留出网络往返的余量

> 60 秒是每个**决定**，不是每手。六个人全程磨到最后一秒的话，一手牌理论上能拖到二十多分钟。真打起来如果嫌慢，业界的常规做法是「基础时间短一些 + 每人一个可消耗的时间池」——想加随时说，协议上只是多一个 `timeBank` 字段。

超时不等于掉线。连续超时若干手才会被请下座位。

## 断线与重连

**断线不立即弃牌**，但**计时照走** —— 否则拔网线就等于无限思考时间，这是个可以被利用的漏洞。

| 时间点 | 行为 |
|---|---|
| 断开瞬间 | 标记 `connected: false`，其他人能看到 |
| 轮到他且超时 | 照常自动过牌/弃牌 |
| 带 token 重连 | 拿回座位，收到一份完整 `state`，无缝继续 |
| 连续 3 手没连上 | 请下座位，筹码保留在座位记录里 |
| 超过 30 分钟没回来 | 释放座位 |

重连不需要重放历史 —— 直接给全量 `state` 就够了，这也是「不做增量同步」的另一个好处。

---

## 机器人补位

- 房间配置 `fillWithBots: true` 时，空位由电脑对手补齐，两个人也能开桌
- 机器人跑在服务器上，消费的是**和真人完全相同的** `viewFor(botId)`
- 机器人也有"思考"延时，节奏和单机版一致
- 真人加入时优先坐空位；没有空位则在**下一手开始前**移除一个机器人，绝不在牌局中途动座位

## 一段完整的时序

```
客户端                                服务器
  │                                     │
  ├─ join {room:"K7QP", name:"老王"} ──▶│
  │◀── welcome {you:3, token:"…"} ──────┤
  │◀── state {view, actionSeq:0} ───────┤
  │                                     │
  │◀── events [hand-start, blind…] ─────┤   新一手开始
  │◀── state {view, actionSeq:0} ───────┤
  │◀── turn {seat:3, deadline, …} ──────┤   轮到我
  │                                     │
  ├─ action {handNumber:47,             │
  │          actionSeq:0,               │
  │          type:"call"} ─────────────▶│
  │◀── events [action] ─────────────────┤
  │◀── state {view, actionSeq:1} ───────┤   序号推进了
  │                                     │
  ├─ action {actionSeq:0, …} ──────────▶│   ← 重复提交（双击）
  │◀── error {code:"stale_action"} ─────┤   ← 被拒，状态不变
```

## 服务器永远不会发出的东西

- 牌堆（`deck`）
- 别人的底牌（摊牌时该亮的除外）
- 随机数种子或发生器状态

**两条出口，两道闸**：

| 出口 | 裁剪函数 | 白名单 |
|---|---|---|
| 状态 | `engine.viewFor(id)` | `VIEW_KEYS` |
| 事件 | `engine.eventsFor(id, events)` | `EVENT_KEYS` |

都由 `tests/view.test.js` 逐字节盯着：六十手全程共 4956 份视图零泄漏，事件通道另测数百条。新增字段必须先登记进白名单才能通过测试。

写协议时才发现事件这条出口之前完全没人管 —— 状态守得再严，旁边留一扇没锁的门也是白搭。

## 待定 / 暂不做

| 项目 | 说明 |
|---|---|
| 观战 | 视图裁剪已支持（`viewFor(null)`），但先不做入口 |
